## 1. 背景と課題（Why）

契約者が自分の契約を操作する API（契約の照会、プラン変更・解約の予約と取り消し、支払方法の登録・変更・削除、請求の履歴、退会）は実装済みだが、契約者が使う画面がない。申込ページも、ログインの画面がないため、トークンを URL で受け取る仮の作りになっている（P-IMP-19）。

その結果、次の問題がある。

- **解約・カードの更新を契約者が自分でできない**。すべて事業者への問い合わせになり、事業者の運用の負担になる。上位のゴール「事業者が課金を自前で作らずに販売できる」を損なう。
- **支払い遅延から回復できない**。支払い失敗のメールにはカードの更新のリンクを載せているが、リンク先の画面がない。回収できるはずの売上を失い、事業者のダッシュボードの「支払い回復率」（console-dashboard）が下がる。
- **複数の事業者の契約をまとめて管理する**という、共通アカウントの価値（US-007）を契約者が体験できない。

マイページは、契約者がスマートフォンからログインし、すべての事業者との契約を確認して、必要な手続き（解約・プラン変更・カードの更新・退会）を自分で完了できるようにする。

## 2. ゴールと成功指標

| ゴール | 成功指標 |
|---|---|
| 契約の手続きを契約者が自分で完了できる | 解約・解約の取り消し・プラン変更・支払方法の変更・退会が、事業者に問い合わせずにマイページだけで完了する（E2E で確認） |
| 支払い遅延から自分で回復できる | 支払い失敗のメールのリンクから、ログイン → カードの登録 → 即時の再決済 → 契約が「有効」に戻るまでを、メールアドレスとパスワード以外の入力なしで完了できる（E2E で確認）。事業者のダッシュボードの支払い回復率で効果を見る |
| 共通アカウントの価値を体験できる | 複数の事業者の契約が 1 つの一覧に、事業者名・プラン名・金額・状態・次の更新日つきで並ぶ |
| スマートフォンで使える | 幅 375px で全画面の閲覧と操作ができる（契約者の主な利用環境はスマートフォンと想定） |

## 3. ユーザーストーリー

| ID | 誰が | 何のために | 何をする |
|---|---|---|---|
| MP-01 | 契約者 | 申し込み・契約を管理するために | メールアドレスとパスワードでアカウントを作り、ログインする。パスワードを忘れたら再設定する |
| MP-02 | 契約者 | 自分の契約を把握するために | すべての事業者との契約を一覧で見て、詳細（期間・次の更新日・金額・予約中の変更・請求の履歴）を確認する |
| MP-03 | 契約者 | 不要になった契約を止めるために | 解約を予約し、気が変わったら取り消す |
| MP-04 | 契約者 | 利用状況に合わせるために | 同じ商品の別のプランへの変更を予約し、取り消す |
| MP-05 | 契約者 | 支払いを続けるために | カードを登録・削除し、契約ごとの支払方法を変える。支払い遅延の契約はその場で再決済する |
| MP-06 | 契約者 | サービスの利用をやめたあと個人情報を残さないために | 退会する |
| MP-07 | 契約者 | 事業者のサイトから申し込むために | 申込ページからログイン（アカウントの作成）をして、申込に戻る |

## 4. 前提条件

- 契約者の認証は、契約者用の Cognito ユーザープール 1 つで行う（スタッフ用とは別。上位の設計のとおり）。ユーザー名はメールアドレスとする。1 つのアカウントで複数の事業者と契約できる（上位 FR-011）。
- 契約者のアカウント（customer モジュールの契約者）は、初めて認証済みで API を呼んだときに作られる（実装済みの JIT）。氏名・メールアドレスは Cognito の属性から同期する。
- マイページはプラットフォーム共通の画面で、特定の事業者のブランドは表示しない。事業者名は契約ごとに表示する。
- カード番号は契約者のブラウザでトークン化し、自社のサーバーは扱わない（上位 NFR-007）。本番は fincode の JS、ローカル・CI は既存の stub のトークン化（申込ページと同じ）を使う。
- 申込（新しい契約）は、事業者のサイトにある申込ページの URL から始める。マイページから事業者・プランを探して申し込む機能は持たない。
- 認可の判定は API が行う。契約者は自分の契約・支払方法・請求だけを操作できる（実装済み。他人の ID は 404）。
- 画面は既存の API を呼ぶ。画面のために足りない API（契約の表示名・変更先のプランの一覧など）は本書の要件として追加する。
- ローカル・CI では MiniStack の Cognito を使う（事業者コンソールで SRP・新規登録の確認コード・パスワードの再設定が動くことを確認済み）。

## 5. 機能要件

### FR-001: アカウントの作成とログイン

- **概要**: 契約者は、メールアドレス・パスワード・氏名でアカウントを作る。メールアドレスに届く確認コードを入力して登録を完了する。登録後はメールアドレスとパスワードでログインする。
  - パスワードの方針：8 文字以上、英字と数字を含む（契約者の使いやすさを優先し、スタッフより緩くする）。
  - ログイン・パスワードの再設定では、アカウントの有無がわかる文言を出さない（ログインの失敗は「メールアドレスまたはパスワードが正しくありません」）。登録の画面で既に登録済みのメールアドレスを入れたときは、「このメールアドレスは登録済みです」と表示し、ログインとパスワードの再設定へ案内する（一般的なサービスと同じ。登録の画面では有無が推測できることを許容する。NFR-005）。
  - 確認コードの再送ができる。確認コードの有効期限は Cognito の既定（24 時間）。
- **関連ストーリー**: MP-01
- **優先度**: Must

```gherkin
Scenario: アカウントを作ってログインする
  Given 登録していないメールアドレス
  When 契約者がメールアドレス・パスワード・氏名を入力し、メールの確認コードを入力する
  Then 登録が完了してログインした状態になり、契約の一覧（空）が表示される

Scenario: 方針に合わないパスワード
  When 7 文字のパスワード、または数字を含まないパスワードで登録する
  Then 登録できず、パスワードの条件が表示される

Scenario: 登録済みのメールアドレス
  Given 登録済みのメールアドレス
  When そのメールアドレスで登録しようとする
  Then 「このメールアドレスは登録済みです」と表示され、ログインとパスワードの再設定への導線が出る

Scenario: 誤った確認コード
  When 誤った確認コードを入力する
  Then 登録は完了せず、「確認コードが正しくありません」と表示される。再送できる

Scenario: ログインの失敗
  When 誤ったパスワードでログインする
  Then 「メールアドレスまたはパスワードが正しくありません」と表示される
```

### FR-002: パスワードの再設定

- **概要**: 契約者は、メールアドレスに届く確認コードで新しいパスワードを設定できる。登録していないメールアドレスでも、画面上は同じ表示にする。
- **関連ストーリー**: MP-01
- **優先度**: Must

```gherkin
Scenario: パスワードを再設定してログインする
  Given 登録済みの契約者
  When 「パスワードを忘れた」から確認コードを受け取り、新しいパスワードを設定する
  Then 新しいパスワードでログインできる
```

### FR-003: セッション

- **概要**: ログインの状態は 30 日保つ（契約者の利用頻度は月に数回程度と想定し、毎回のログインを求めない）。ログアウトすると、このブラウザの認証情報を消し、トークンを失効させる。トークンの期限が切れたら、ログイン画面に移り、ログイン後に元の画面に戻る。
- **関連ストーリー**: MP-01
- **優先度**: Must

```gherkin
Scenario: 期限切れの後、元の画面に戻る
  Given ログインの期限が切れた契約者が、メールのリンクから契約の画面を開く
  When ログインする
  Then 開こうとした契約の画面が表示される
```

### FR-004: 契約の一覧

- **概要**: すべての事業者との契約を一覧で表示する。各契約に、事業者名・商品名・プラン名・金額（税込）と請求の周期・状態・次の更新日（または利用できる期限・解約日）を表示する。
  - 並び順：要対応（支払い遅延）を先頭に、次に有効・トライアル中、最後に解約済み。同じ区分の中は新しい順。
  - 解約済みの契約は、既定では折りたたんで件数だけを示し、開くと表示する。
  - 支払い遅延の契約があれば、一覧の上部に「お支払いが確認できない契約があります」の案内と、支払方法の変更への導線を出す。
- **関連ストーリー**: MP-02
- **優先度**: Must

```gherkin
Scenario: 複数の事業者の契約をまとめて表示する（上位 FR-018）
  Given 契約者が事業者 A と事業者 B の両方と契約している
  When マイページを開く
  Then 両方の契約が、事業者名・プラン名・金額・状態・次の更新日つきで表示される

Scenario: 支払い遅延の契約を先頭に出す
  Given 有効な契約 2 件と支払い遅延の契約 1 件がある
  When マイページを開く
  Then 支払い遅延の契約が先頭に表示され、上部に支払方法の変更への案内が出る

Scenario: 契約がない
  Given 契約がない契約者
  When マイページを開く
  Then 「契約はまだありません。事業者のサイトから申し込めます」と表示される
```

### FR-005: 契約の詳細と請求の履歴

- **概要**: 契約の詳細で、事業者名・商品名・プラン名・金額・状態・利用できるか（利用権）・現在の期間・次の更新日・トライアルの期間・適用中の割引（残りの回数）・支払方法（カードの下 4 桁と有効期限）・予約中のプラン変更（変更先と適用日）・予約中の解約（終了日）を表示する。請求の履歴（期間・金額・状態・支払日）を新しい順に表示する。
- **関連ストーリー**: MP-02
- **優先度**: Must

```gherkin
Scenario: 解約を予約した契約の詳細
  Given 次の更新日が 11-15 の契約の解約を予約している
  When 契約の詳細を開く
  Then 「11 月 14 日まで利用できます。11 月 15 日に解約されます」と表示され、解約の取り消しができる

Scenario: 他人の契約
  When 他人の契約の ID で詳細を開く
  Then 「見つかりません」と表示される（API は 404）
```

### FR-006: 解約の予約と取り消し

- **概要**: 契約者は解約を予約できる（上位 FR-016）。確認の画面で、利用できる期限と解約日、解約すると次の更新で請求しないことを示してから確定する。期間の終了日までは取り消せる。
  - 支払い遅延の契約の解約は即時に解約済みになる（上位 FR-016）。確認の画面でそのことを明示する。
  - トライアル中の解約は課金されないことを明示する（上位 FR-014）。
  - 事業者の停止などシステムによる解約（取り消せないもの）は、取り消しの操作を出さない。
- **関連ストーリー**: MP-03
- **優先度**: Must

```gherkin
Scenario: 解約を予約して取り消す
  Given 有効な契約
  When 解約を予約し、その後取り消す
  Then 予約後は終了日が表示され、取り消し後は次の更新日に戻る

Scenario: 支払い遅延の契約を解約する
  Given 支払い遅延の契約
  When 解約を確定する
  Then 確認の画面に「すぐに解約され、未払いの請求の再請求は止まります」と表示され、確定すると契約は解約済みになる

Scenario: 更新の処理中
  Given 更新日の請求の処理中の契約
  When 解約を予約する
  Then API の応答の適用日（次の期間の終了日）を画面に表示する
```

### FR-007: プラン変更の予約と取り消し

- **概要**: 契約者は、同じ商品の公開中の別のプランへの変更を予約できる（上位 FR-015）。変更先の候補（プラン名・金額・周期）を表示し、適用日（次の更新日）と、次の更新から請求する金額を示してから確定する。予約は取り消せる。解約を予約している契約では、プラン変更を選べない（解約の取り消しを促す）。
- **関連ストーリー**: MP-04
- **優先度**: Must

```gherkin
Scenario: 上位のプランへの変更を予約する
  Given 980 円の月額プランの有効な契約（次の更新日 11-15）、同じ商品に 1,980 円のプランがある
  When 1,980 円のプランへの変更を確定する
  Then 「11 月 15 日から 1,980 円／月」と表示され、今日の請求は発生しない

Scenario: 変更先がない
  Given 同じ商品に公開中の別のプランがない
  When 契約の詳細を開く
  Then プラン変更の操作は表示されない

Scenario: 変更先が非公開になった
  Given 変更の画面を開いた後に、変更先のプランが非公開になった
  When 変更を確定する
  Then 「このプランには変更できません」と表示され、候補を読み直す
```

### FR-008: 支払方法の管理

- **概要**: 契約者はカードを登録・削除できる（上位 FR-012）。カード番号はブラウザでトークン化して登録する。登録済みのカードは下 4 桁・ブランド・有効期限・期限切れの印・使っている契約の数とともに一覧する。
  - 使っている契約があるカードは削除できない（上位 FR-012）。削除しようとしたら、使っている契約と、支払方法の変更への導線を示す。
- **関連ストーリー**: MP-05
- **優先度**: Must

```gherkin
Scenario: カードを登録する
  When 契約者が支払方法の画面でカードを登録する
  Then 一覧に下 4 桁と有効期限のカードが追加される。カード番号は自社のサーバーに送られない

Scenario: 使っているカードは削除できない
  Given カード C が有効な契約の支払方法になっている
  When カード C を削除しようとする
  Then 削除できず、使っている契約と変更の方法が表示される

Scenario: トークン化の失敗
  When カード番号の形式が正しくない
  Then 「カード情報を確認できませんでした」と表示され、登録されない
```

### FR-009: 契約の支払方法の変更と即時の再決済

- **概要**: 契約者は、契約ごとに支払方法を変更できる。登録済みのカードを選ぶか、その場で新しいカードを登録して選ぶ。支払い遅延の契約では、変更と同時に未払いの請求を再決済し、結果を表示する（上位 FR-017）。
- **関連ストーリー**: MP-05
- **優先度**: Must

```gherkin
Scenario: 支払い遅延の契約でカードを変えて回復する（上位 FR-017）
  Given 支払い遅延の契約と、未払いの請求 1 件
  When 契約者が新しいカードを登録してこの契約の支払方法にする
  Then 未払いの請求が再決済され、「お支払いが完了しました」と表示され、契約は有効に戻る

Scenario: 再決済も失敗する
  Given 支払い遅延の契約
  When 新しいカードでの再決済も失敗する
  Then 「お支払いができませんでした。別のカードをお試しください」と表示され、契約は支払い遅延のまま

Scenario: 結果がすぐにわからない
  When 再決済の結果が決済代行から返らない
  Then 「お支払いを確認しています」と表示し、画面を読み直すと結果が反映される
```

### FR-010: 退会

- **概要**: 契約者は退会できる。有効・支払い遅延・トライアル中の契約が残っていれば退会できず、残っている契約と解約の手順を示す（上位 FR-011）。退会は取り消せないことを示し、確認のためにメールアドレスの入力を求めてから確定する。退会すると、個人情報はマスキングされ（上位 NFR-015）、ログアウトする。
  - 退会後は同じアカウントでログインしても使えない（「退会済みのアカウントです」）。同じメールアドレスで新しく登録した場合は、別の新しい契約者として扱う（§9 #1）。
- **関連ストーリー**: MP-06
- **優先度**: Must

```gherkin
Scenario: 契約が残っていると退会できない
  Given 有効な契約が 1 件ある
  When 退会しようとする
  Then 退会できず、残っている契約と解約の手順が表示される

Scenario: 退会する
  Given 契約がすべて解約済み
  When メールアドレスを入力して退会を確定する
  Then 退会が完了し、ログアウトして「退会しました」と表示される
```

### FR-011: 申込ページからのログイン

- **概要**: 申込ページ（`/checkout?plan_id=…`）をログインせずに開いたときは、「ログインして申し込む」「アカウントを作って申し込む」を表示する。マイページのログイン（または登録）を終えたら、申込ページに戻り、そのまま申し込める。
- **関連ストーリー**: MP-07
- **優先度**: Must

```gherkin
Scenario: 新しい契約者が申込ページからアカウントを作って申し込む
  Given ログインしていない人が事業者のサイトから申込ページを開く
  When 「アカウントを作って申し込む」からアカウントを作る
  Then 申込ページに戻り、プランの内容が表示され、カードを入力して申し込める
```

### FR-012: メールのリンクの行き先

- **概要**: 契約者へのメール（上位 FR-023）のリンクをマイページに向ける。支払い失敗のメールは、その契約の支払方法の変更の画面に向ける。ログインしていなければログインの後にその画面を開く（FR-003）。
- **関連ストーリー**: MP-05
- **優先度**: Must

```gherkin
Scenario: 支払い失敗のメールから回復する
  Given 支払い遅延になり、支払い失敗のメールが届いた
  When メールのリンクを開いてログインする
  Then その契約の支払方法の変更の画面が開く
```

### FR-013: アカウントの情報

- **概要**: 登録しているメールアドレスと氏名を表示する。ログアウト・パスワードの変更（現在のパスワードと新しいパスワード）・退会への導線を置く。
- **関連ストーリー**: MP-01, MP-06
- **優先度**: Should

```gherkin
Scenario: パスワードを変更する
  When 現在のパスワードと新しいパスワードを入力して変更する
  Then 次回から新しいパスワードでログインできる
```

### FR-014: 共通の操作とエラーの表示

- **概要**: 取り消せない操作（解約・退会・カードの削除）は確認の画面を出す。API のエラーはエラーコードごとの日本語の文言で表示し、問い合わせ番号（相関 ID）を添える。操作の結果は短い通知で示す。読み込み中はスケルトンを表示する。状態の競合（更新の処理中など）は「状態が変わりました。読み直してください」と表示して読み直す。
- **関連ストーリー**: 全体
- **優先度**: Must

```gherkin
Scenario: サーバーのエラー
  When API が 500 を返す
  Then 「処理に失敗しました」と問い合わせ番号が表示され、操作はやり直せる
```

## 6. 非機能要件

| ID | 区分 | 要件 |
|---|---|---|
| NFR-001 | 性能 | 画面の主要な API（契約の一覧・詳細）は p95 500ms 以内（上位 NFR-002）。初回の表示は 4G 回線のスマートフォンで 3 秒以内を目安とし、画面の JS は必要なものだけを読み込む |
| NFR-002 | 可用性 | 月間 99.9%（上位 NFR-004。マイページは対象）。決済代行の障害時も、閲覧と予約の操作（解約・プラン変更）は使える（上位 NFR-005） |
| NFR-003 | セキュリティ | カード番号は自社のサーバーを通らない（上位 NFR-007）。CSP で外部のスクリプトを許すのはトークン化の JS だけ。トークンは本書の画面の外（申込ページへの受け渡し）では URL のフラグメントだけで渡し、サーバーのログ・Referer に出さない |
| NFR-004 | セキュリティ | 他人の契約・支払方法・請求は見えない・操作できない（API で 404。自動テストで保証。上位 NFR-008） |
| NFR-005 | セキュリティ | ログイン・パスワードの再設定では、アカウントの有無を推測できる応答を返さない（登録の画面は FR-001 のとおり許容する）。ログインの試行の制限は Cognito の既定に従う |
| NFR-006 | 個人情報 | ログにメールアドレス・氏名・カードの情報を出さない（上位 NFR-017 ④）。画面のエラーの報告もこれらを含めない |
| NFR-007 | 使いやすさ | スマートフォン（幅 375px）を主に設計する。タップの対象は 44px 以上。日本語のみ。金額は税込の円、日付は JST |
| NFR-008 | アクセシビリティ | フォームの項目にラベル、エラーは項目のそばに文字で示す（色だけに頼らない）。キーボードで操作できる |
| NFR-009 | テスト | 受け入れ条件はブラウザの E2E（MiniStack の Cognito・stub の決済）で確かめる。既存の API の E2E は開発用 JWT のまま |

## 7. 状態遷移

契約の状態の遷移は上位の設計（subscription.md）のとおりで、本書では変えない。画面に出す操作は状態で決める。

| 契約の状態 | 解約の予約 | 解約の取り消し | プラン変更の予約・取り消し | 支払方法の変更 |
|---|---|---|---|---|
| トライアル中 | ○（課金されない旨を表示） | ○（予約中で、取り消せるとき） | ○ | ○ |
| 有効 | ○ | ○（予約中で、取り消せるとき） | ○（解約の予約がないとき） | ○ |
| 支払い遅延 | ○（即時に解約） | — | — | ○（即時に再決済） |
| 解約済み | — | — | — | — |

契約者のアカウントの状態：未登録 →（登録・確認コード）→ 有効 →（退会）→ 退会済み（ログインしても使えない）。

## 8. スコープ外（やらないこと）

- マイページからの新しい申込（事業者・プランを探す機能）。申込は事業者のサイトの申込ページから
- ソーシャルログイン（Google・Apple など）、多要素認証、パスキー（将来）
- メールアドレス・氏名の変更（将来。当面は Cognito に登録した値のまま）
- 領収書・適格請求書の表示と PDF の出力（上位 NFR-012 の将来の拡張）
- 数量の変更、即時のプラン変更・日割り、契約の一時停止
- 解約済みの契約の再開（もう一度申し込む）
- 事業者ごとのブランド（ロゴ・色）の表示、多言語
- 事業者への問い合わせの機能、通知の設定（メールの配信停止など）
- ネイティブアプリ、プッシュ通知
- 申込ページの作り直し（本書では FR-011 のログインの導線だけを足す）
