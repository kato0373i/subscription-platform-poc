## 1. 背景と課題（Why）

プラットフォームの運営者の操作（事業者の審査・承認・停止、最初のオーナーの招待、決済の結果の確定、照合の不整合の確認、更新処理の再実行、請求の再決済、Webhook の再送、監査ログの確認）は ops API として実装済みだが、画面がない。今は API を直接呼ぶしかなく、次の問題がある。

- **事業者の受け入れが滞る**。審査待ちの事業者に気づく仕組みがなく、承認の操作も API の知識が要る。上位のゴール「事業者が開発なしで販売を始められる」の入口がボトルネックになる。
- **お金に関わる異常に気づけない・直せない**。結果が不明な決済・照合の不整合・更新処理の失敗は、放置すると二重請求や取りこぼし（売上の欠損）につながる（上位 NFR-006・NFR-014）。今は誰も一覧で見られない。
- **作業の記録の確認が難しい**。監査ログは API で検索できるが、問い合わせ・監査の対応で人が見られる形になっていない。

運営者コンソールは、運営者が毎朝開いて「要対応」を確認し、事業者の受け入れと、お金に関わる異常の是正を、画面から安全に（確認つき・監査つきで）行えるようにする。

## 2. ゴールと成功指標

| ゴール | 成功指標 |
|---|---|
| 異常に気づける | ホームに、審査待ちの事業者・結果が不明な決済・未対応の照合の不整合・当日の更新処理の失敗・実行中の一括解約の件数が並び、クリックで対応の画面に移れる |
| 事業者を画面だけで受け入れ・停止できる | 事業者の登録 → 最初のオーナーの招待 → 承認、と、停止 → 一括解約の進み具合の確認が、API を使わずにできる（E2E で確認） |
| お金に関わる異常を是正できる | 結果が不明な決済の手動での確定、照合の不整合の確認と対応済みにすること、更新処理の再実行、請求の再決済、Webhook の再送が画面からでき、すべて監査ログに残る（上位 NFR-014） |
| 誤操作を防ぐ | 取り消せない操作・お金に関わる操作は、対象と影響を示す確認を経てから実行する |

## 3. ユーザーストーリー

| ID | 誰が | 何のために | 何をする |
|---|---|---|---|
| OP-01 | 運営者 | 安全に操作するために | 運営者のアカウント（メールアドレスとパスワード）でログインする |
| OP-02 | 運営者 | 異常に早く気づくために | ホームで要対応の件数を見て、対応の画面に移る |
| OP-03 | 運営者 | 事業者を受け入れるために | 事業者を登録し、最初のオーナーを招待し、審査して承認する |
| OP-04 | 運営者 | 規約違反の事業者を止めるために | 事業者を停止し、契約の一括解約の進み具合を確かめる |
| OP-05 | 運営者 | 決済の取りこぼし・二重請求を防ぐために | 結果が不明な決済を確認して確定し、照合の不整合を確認して対応済みにする |
| OP-06 | 運営者 | 更新処理の障害から復旧するために | 課金日ごとの更新処理の結果を見て、必要なら再実行する。個別の請求を再決済する |
| OP-07 | 運営者 | 事業者のシステム連携の障害を助けるために | 事業者の Webhook の配信を検索して再送する |
| OP-08 | 運営者 | 問い合わせ・監査に答えるために | 監査ログを条件で検索し、変更の前後を確かめる |

## 4. 前提条件

- 運営者の認証は、運営者用の Cognito ユーザープール（既存）で行い、グループ `operators` に属するアカウントだけが ops API を使える（実装済みの認可）。アカウントは自己登録できず、インフラの管理者が作る（人数は数名）。
- 運営者の権限は 1 種類（すべての ops の操作ができる）。権限の細分化は範囲外（§8）。
- 運営者の操作は、既存の監査のしくみ（ops API の監査ミドルウェア）ですべて記録される。
- 画面は既存の ops API を呼ぶ。画面のために足りない API（結果が不明な決済の一覧、照合の不整合を対応済みにする操作）は本書の要件として足す。
- 運営者は PC で使う（スマートフォン対応は範囲外）。
- ローカル・CI では MiniStack の Cognito を使う（グループが ID トークンの `cognito:groups` に入ることを確認済み）。

## 5. 機能要件

### FR-001: ログイン

- **概要**: 運営者はメールアドレスとパスワードでログインする。初回は管理者が発行した仮パスワードから新しいパスワードを設定する。パスワードの再設定はメールの確認コードで行う。グループ `operators` に属さないアカウントは、ログインできても画面を使えない（「運営者の権限がありません」）。
  - 無操作 30 分で自動でログアウトする（権限が強いので事業者コンソールの 8 時間より短くする）。ログインの状態の上限は 8 時間。
  - パスワードの方針はスタッフと同じ（12 文字以上・大小英字・数字・記号）。
- **関連ストーリー**: OP-01
- **優先度**: Must

```gherkin
Scenario: 運営者がログインする
  Given グループ operators に属する運営者のアカウント
  When メールアドレスとパスワードでログインする
  Then ホームが表示される

Scenario: 運営者でないアカウント
  Given グループ operators に属さないアカウント
  When ログインする
  Then 「運営者の権限がありません」と表示され、ops の画面は使えない

Scenario: 無操作でログアウトする
  Given ログインしてから 30 分操作していない
  When 画面を操作しようとする
  Then ログインの画面に移り、「一定時間操作がなかったためログアウトしました」と表示される
```

### FR-002: ホーム（要対応）

- **概要**: ホームに次の件数を表示し、クリックで対応の画面に移る：審査待ちの事業者、結果が不明な決済（確定していない試行）、未対応の照合の不整合、当日の更新処理の結果（成功・失敗・処理中）、停止中の事業者。件数が 0 でない「要対応」は目立たせる。
- **関連ストーリー**: OP-02
- **優先度**: Must

```gherkin
Scenario: 審査待ちの事業者に気づく
  Given 審査待ちの事業者が 2 社ある
  When 運営者がホームを開く
  Then 「審査待ちの事業者 2 社」が表示され、クリックすると審査待ちで絞り込んだ事業者の一覧が開く
```

### FR-003: 事業者の一覧と登録

- **概要**: 事業者を状態（審査待ち・有効・停止中）で絞り込んで一覧する（新しい順・ページング）。事業者を名前で登録し（審査待ちになる）、続けて最初のオーナーをメールアドレス・氏名で招待できる（招待メールが届く。business-console FR-006）。
- **関連ストーリー**: OP-03
- **優先度**: Must

```gherkin
Scenario: 事業者を登録してオーナーを招待する
  When 運営者が事業者名「ミライ書店」を登録し、オーナーのメールアドレスを入力して招待する
  Then 事業者が審査待ちで作られ、オーナーに招待メールが届く
```

### FR-004: 事業者の詳細・承認・停止

- **概要**: 事業者の詳細で、名前・状態・fincode のショップ ID・承認日時・停止日時と理由を表示する。
  - 承認：審査待ちの事業者を、fincode のショップ ID を入力して承認する（上位 FR-001）。同じショップ ID が他の事業者で使われていればエラー。
  - 停止：有効な事業者を、理由を入力し、事業者名の入力で確認してから停止する（上位 FR-026）。停止すると契約の一括解約が始まることを確認の画面で示す。
  - オーナーの追加の招待（招待をやり直す場合など）ができる。
- **関連ストーリー**: OP-03, OP-04
- **優先度**: Must

```gherkin
Scenario: 事業者を承認する
  Given 審査待ちの事業者
  When 運営者がショップ ID を入力して承認する
  Then 事業者は有効になる

Scenario: 事業者を停止する
  Given 有効な事業者に契約がある
  When 運営者が理由を入力し、事業者名を入力して停止を確定する
  Then 事業者は停止中になり、一括解約のジョブが表示される

Scenario: 確認の入力が違う
  When 停止の確認で別の名前を入力する
  Then 停止できない
```

### FR-005: 一括解約の進み具合

- **概要**: 事業者の詳細に、停止による一括解約のジョブ（状態・処理済み・期間の終了で解約・即時解約・失敗の件数・失敗した契約）を表示する。実行中は自動で読み直す。
- **関連ストーリー**: OP-04
- **優先度**: Must

```gherkin
Scenario: 一括解約が終わる
  Given 停止した事業者の一括解約が実行中
  When 運営者が事業者の詳細を開いている
  Then 件数が更新され、終わると「完了」と表示される
```

### FR-006: 結果が不明な決済

- **概要**: 結果が確定していない決済の試行（結果不明・処理中・非同期の確認待ち）を、古い順に一覧する（事業者・金額・状態・依頼日時・経過時間）。試行の詳細（請求・契約者・決済代行の参照・失敗の情報）を表示し、成功または失敗として手動で確定できる（上位 NFR-014。決済代行の管理画面などで確認した結果を、根拠のメモとともに入力する）。
  - 確定の前に「決済代行で確認した結果か」を確認する。確定は取り消せない。
  - 自動の照合（resolve_unknown）で確定したものは一覧から消える。
- **関連ストーリー**: OP-05
- **優先度**: Must

```gherkin
Scenario: 結果が不明な決済を失敗として確定する
  Given 結果が不明なまま 30 秒以上たった試行
  When 運営者が根拠のメモを入力して「失敗」として確定する
  Then 試行は失敗になり、一覧から消え、監査ログに残る

Scenario: 既に確定した試行
  Given 運営者が画面を開いた後に、自動の照合で確定した試行
  When 確定しようとする
  Then 「既に確定しています」と表示され、一覧を読み直す
```

### FR-007: 照合の不整合

- **概要**: 日次の照合（上位 FR-024）が見つけた不整合を、営業日・状態（未対応・対応済み）で絞り込んで一覧する（種類・事業者・決済代行の参照・詳細）。関連する試行の詳細に移れる。調査を終えたら、メモを入力して「対応済み」にできる。
- **関連ストーリー**: OP-05
- **優先度**: Must

```gherkin
Scenario: 不整合を対応済みにする
  Given 未対応の不整合
  When 運営者がメモを入力して対応済みにする
  Then 状態が対応済みになり、ホームの未対応の件数が減る
```

### FR-008: 更新処理（課金日）

- **概要**: 課金日を選び、その日の更新処理の投入の記録（回・きっかけ・状態・投入件数・開始と終了）と、更新の結果の集計（成功・支払い失敗・終了・処理中・失敗）を表示する。必要なら再実行できる（確認つき。投入済みで終わっていない更新を再開し、二重に請求しない）。
- **関連ストーリー**: OP-06
- **優先度**: Must

```gherkin
Scenario: 更新処理を再実行する
  Given 課金日の更新処理に「処理中」のまま止まった更新がある
  When 運営者がその日の再実行を確定する
  Then 再実行の記録が追加される
```

### FR-009: 請求の再決済

- **概要**: 決済の試行の詳細などから、その請求の再決済を依頼できる（確認つき。上位 NFR-014）。請求の ID を入力して依頼することもできる。回収できない状態の請求・処理中の請求はエラーの理由を示す。
- **関連ストーリー**: OP-06
- **優先度**: Should

```gherkin
Scenario: 回収できない請求
  Given 支払い済みの請求
  When 再決済を依頼する
  Then 「この請求は再決済できません」と表示される
```

### FR-010: Webhook の配信の検索と再送

- **概要**: 事業者を選び、Webhook の配信を状態で絞り込んで一覧し、失敗・中止の配信を再送できる（確認つき）。
- **関連ストーリー**: OP-07
- **優先度**: Should

```gherkin
Scenario: 失敗した配信を再送する
  Given 事業者の失敗した配信
  When 運営者が再送する
  Then 手動の新しい配信が作られる
```

### FR-011: 監査ログ

- **概要**: 監査ログを、事業者・操作（action）・操作した人・期間で絞り込んで一覧する（新しい順・ページング）。行を開くと、変更の前後・結果・相関 ID・経路を表示する。
- **関連ストーリー**: OP-08
- **優先度**: Must

```gherkin
Scenario: 事業者の停止の記録を探す
  When 運営者が操作「tenant.suspend」で検索する
  Then 停止の記録が表示され、開くと理由と操作した運営者がわかる
```

### FR-012: 共通の操作とエラーの表示

- **概要**: 事業者コンソールと同じ（business-console FR-016）：取り消せない操作は確認、API のエラーは日本語の文言と問い合わせ番号（相関 ID）、操作の結果は通知、読み込み中はスケルトン。ID はコピーできる。
- **関連ストーリー**: 全体
- **優先度**: Must

```gherkin
Scenario: 権限のない操作
  When API が 403 を返す
  Then 「運営者の権限がありません」と表示される
```

## 6. 非機能要件

| ID | 区分 | 要件 |
|---|---|---|
| NFR-001 | セキュリティ | ops API はグループ `operators` の ID トークンだけを受け付ける（実装済み）。画面の表示の制御は使いやすさのためで、境界は API |
| NFR-002 | セキュリティ | 無操作 30 分でログアウト、ログインの上限 8 時間。トークンは事業者コンソールと同じく CSP で守る |
| NFR-003 | 監査 | 運営者の書き込みの操作はすべて監査ログに残る（既存）。新しく足す操作（照合の不整合の対応済み）も監査の対象にする |
| NFR-004 | 個人情報 | 画面に出す契約者の情報は ID までにし、氏名・メールアドレスは出さない（運営者の業務に要らない。必要なら事業者に問い合わせる） |
| NFR-005 | 性能 | 一覧の API は p95 500ms 以内（上位 NFR-002）。結果が不明な決済の一覧は、確定していない試行のインデックス（既存）で引く |
| NFR-006 | 使いやすさ | PC（幅 1280px 以上）を前提にする。見た目は事業者コンソールと同じ方針（Stripe を参考） |
| NFR-007 | テスト | 受け入れ条件はブラウザの E2E（MiniStack の Cognito の運営者のプール）で確かめる |

## 7. 状態遷移

事業者の状態（上位 FR-001・FR-026）：審査待ち →（承認）→ 有効 →（停止）→ 停止中。停止中から戻す操作は範囲外。

照合の不整合：未対応 →（対応済みにする）→ 対応済み（戻さない）。

## 8. スコープ外（やらないこと）

- 運営者の権限の細分化（閲覧のみなど）、運営者のアカウントの管理画面（作成・削除はインフラの管理者が行う）
- 多要素認証（本番では必須にする方針。§9 #1）、IP アドレスの制限（本番の WAF で行う。§9 #2）
- 事業者の停止の解除、事業者の削除、事業者の情報の編集
- 契約・請求の横断検索と、契約者の個人情報の表示（NFR-004）
- 返金・請求の取り消し・金額の修正
- 売上・手数料の集計、事業者への精算
- スマートフォン対応
