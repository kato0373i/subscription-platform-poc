## 1. 背景と課題（Why）

事業者コンソールで販売の準備と問い合わせ対応はできるようになったが、事業者は「事業がうまくいっているか」を画面で判断できない。契約の一覧を数えたり、Webhook で受けたデータを自社で集計したりしないと、売上の伸び・解約の多さ・トライアルの効果がわからない。サブスクリプションの事業では、毎月の経常収益（MRR）の積み上がりが成果そのもので、それを分解した指標（獲得・解約・転換・回収）を見て打ち手を決める。

ダッシュボードは、事業者がログインして最初に、自社の KGI（MRR とその純増）と、それを動かす KPI を確認し、必要な打ち手（支払い遅延の対応、解約の多いプランの見直しなど）にすぐ進めるようにする。あわせて、外出先でも状況を確認・対応できるよう、コンソール全体をスマートフォンの幅で使えるようにする。

## 2. ゴールと成功指標

| ゴール | 成功指標 |
|---|---|
| 事業の成果を一目で把握できる | ダッシュボードを開くと、MRR・純増 MRR とその内訳・目標に対する達成率が最初に表示される |
| 打ち手を決める材料がそろう | 獲得・解約・トライアル転換・支払い回収・売上の KPI が、当月と前月の比較・12 か月の推移で確認できる |
| 数字が正しく、新しい | 指標は契約・請求のイベントから作り、イベントの発生から 1 分以内に反映される。E2E で、契約の開始・転換・解約・回収の後の数値が定義どおりであることを確かめる |
| 外出先でも使える | 幅 375px（iPhone SE 相当）で、全画面の閲覧と主な操作ができる（横スクロールでページが崩れない） |

## 3. ユーザーストーリー

| ID | 誰が | 何のために | 何をする |
|---|---|---|---|
| DB-01 | スタッフ（全ロール） | 事業の成果を把握するために | ダッシュボードで MRR・純増 MRR・目標の達成率を見る |
| DB-02 | スタッフ（全ロール） | 伸び悩みの原因を探すために | 獲得・解約・転換・回収・売上の KPI を、当月・前月・過去 12 か月で比べる |
| DB-03 | オーナー・管理者 | 組織の目標を共有するために | 月次の MRR の目標を設定する |
| DB-04 | スタッフ（全ロール） | すぐ対応すべきことに気づくために | 支払い遅延の契約・トライアル終了間近の契約の件数を見て、該当する契約の一覧に移る |
| DB-05 | スタッフ（全ロール） | 外出先で確認・対応するために | スマートフォンでコンソールを使う |

## 4. 前提条件

- 指標は事業者（テナント）ごとに集計し、他の事業者の数値は一切含めない・表示しない。
- 集計の元は、既存のドメインイベント（`subscription.*`・`billing.invoice_*`）とする。新しいイベントは作らない。価格は catalog の価格バージョンから引く（価格バージョンは追記のみで変わらない）。
- 日付・月の区切りは日本時間（JST）。日付は業務時刻（dev clock を含む。イベントの `occurred_at`）で決める。
- 金額は税込の円。
- 本書の機能を本番に出す時点より前の契約の取り込み（過去データの再集計）は、本書の範囲外とする（PoC の環境は空の状態から始まるため）。§9 #1。

## 5. 指標の定義（PdM の決定）

本書で使う指標の正式な定義。画面・API・テストはこの定義に従う。

### 5.1 用語

| 用語 | 定義 |
|---|---|
| 有料契約 | 状態が `active` または `past_due` の契約。`trialing`（トライアル中）・`pending_initial`（申込中）・`canceled` は含めない。`past_due` は回収中で、解約が確定するまでは収益の見込みとして数える（一般的な SaaS 指標の慣行） |
| 月額換算額 | その契約のプランの価格（契約時の価格バージョンの金額・税込）× 数量。年払いは 12 で割り、円未満を四捨五入する |
| 当月 | JST の暦月。当月は月初から現在まで、過去の月は月末まで |

### 5.2 KGI

| 指標 | 定義 |
|---|---|
| MRR（月次経常収益） | その時点の有料契約の月額換算額の合計。割引（クーポン）は差し引かない（定価ベース。クーポンの影響は入金額で見る） |
| ARR | MRR × 12（参考表示） |
| 純増 MRR（Net New MRR） | 期間中の 新規 MRR ＋ 増額 MRR − 減額 MRR − 解約 MRR。期首の MRR ＋ 純増 MRR ＝ 期末の MRR になる |
| 新規 MRR | 契約の月額換算の MRR が 0 から正に変わったとき（トライアルなしの契約の開始、トライアルからの有料化）の額 |
| 増額 MRR・減額 MRR | 有料契約のまま、プランの変更で月額換算額が増えた・減ったときの差額 |
| 解約 MRR | 有料契約が解約済みになったときの、解約前の月額換算額 |
| MRR の目標の達成率 | 当月の MRR ÷ 当月の目標（目標が未設定なら表示しない） |

### 5.3 KPI

| 区分 | 指標 | 定義 |
|---|---|---|
| 獲得 | 新規契約数 | 期間中に始まった契約の数（トライアルの開始を含む。`subscription.started`） |
| 獲得 | 新規 MRR | §5.2 |
| 継続 | 解約数 | 期間中に解約済みになった契約の数。理由（契約者の解約・支払い失敗・事業者の停止）ごとの内訳を持つ。トライアル中の解約も数える |
| 継続 | 解約率（契約数） | 期間中に解約済みになった有料契約の数 ÷ 期首の有料契約の数。期首が 0 なら表示しない（「—」） |
| 継続 | 収益の解約率 | （解約 MRR ＋ 減額 MRR）÷ 期首の MRR。期首が 0 なら「—」 |
| 転換 | トライアル転換率 | 期間中にトライアルの結果が決まった契約のうち、有料化した割合。有料化 ＝ トライアルから初めて有料契約（`active` または `past_due`）になった。不成立 ＝ 一度も有料契約にならずに解約済みになった。分母は 有料化 ＋ 不成立。分母が 0 なら「—」 |
| 回収 | 支払い回復率 | 期間中に支払い遅延の結果が決まった契約のうち、回復した割合。回復 ＝ `past_due` から `active` に戻った（`subscription.recovered`）。不成立 ＝ 支払い失敗で解約済みになった（理由 `dunning`）。分母が 0 なら「—」 |
| 売上 | 入金額 | 期間中に支払われた請求の合計（税込。`billing.invoice_paid` の金額）。初回・更新の内訳を持つ |
| 売上 | ARPU | MRR ÷ 有料契約の数（有料契約が 0 なら「—」） |
| 状況 | 有料契約数・トライアル中の契約数・支払い遅延の契約数 | その時点の数 |
| 状況 | トライアル終了間近 | トライアル中で、トライアルの終了日が今日から 7 日以内の契約の数 |

## 6. 機能要件

### FR-001: KGI の表示

- **概要**: ダッシュボードの最上部に、選んだ月の MRR（当月なら現在値、過去の月なら月末の値）、前月末からの増減、ARR、純増 MRR とその内訳（新規・増額・減額・解約）を表示する。MRR の 12 か月の推移を折れ線で示す。
- **関連ストーリー**: DB-01
- **優先度**: Must

```gherkin
Scenario: 当月の MRR と純増の内訳を表示する
  Given 月初の MRR が 1,980 円で、当月に 980 円のプランが 2 件始まり、1,980 円のプランが 1 件解約された
  When スタッフがダッシュボードを開く
  Then MRR は 1,960 円、純増 MRR は −20 円（新規 1,960 円・解約 1,980 円）と表示される

Scenario: 年払いのプランは月額に換算する
  Given 年額 9,800 円のプランの有料契約が 1 件だけある
  Then MRR は 817 円と表示される
```

### FR-002: MRR の目標

- **概要**: オーナー・管理者は、月ごとの MRR の目標（円）を設定・変更・削除できる。目標がある月は、KGI の欄に目標と達成率（進捗のバー）を表示する。閲覧者は見るだけ。
- **関連ストーリー**: DB-03
- **優先度**: Should

```gherkin
Scenario: 目標を設定すると達成率が表示される
  Given 当月の MRR が 1,960 円
  When 管理者が当月の目標を 10,000 円に設定する
  Then 目標 10,000 円・達成率 19.6% が表示される

Scenario: 閲覧者は目標を変更できない
  Given 閲覧者がダッシュボードを開いている
  Then 目標の設定は無効で表示され、API で設定しようとすると 403 になる

Scenario: 不正な目標
  When 0 円以下、または 10 億円を超える目標を保存する
  Then 400 になり、目標は変わらない
```

### FR-003: KPI の表示

- **概要**: 選んだ月の KPI（§5.3）を、区分（獲得・継続・転換・回収・売上）ごとのカードで表示する。各カードに前月の値と増減を示す。率の指標は分子・分母も示し（例：「2 / 3 件」）、分母が 0 なら「—」とする。
- **関連ストーリー**: DB-02
- **優先度**: Must

```gherkin
Scenario: トライアル転換率
  Given 当月にトライアルが終わった契約が 3 件あり、2 件が有料化し、1 件がトライアル中に解約された
  Then トライアル転換率は 66.7%（2 / 3 件）と表示される

Scenario: 支払い回復率
  Given 当月に支払い遅延の契約が 1 件回復し、1 件が支払い失敗で解約された
  Then 支払い回復率は 50.0%（1 / 2 件）と表示される

Scenario: 分母が 0
  Given 期首の有料契約が 0 件
  Then 解約率は「—」と表示される
```

### FR-004: 推移

- **概要**: 過去 12 か月（選んだ月を含む）の月ごとの推移を表示する：MRR、新規契約数と解約数、入金額。選んだ月の日ごとの MRR の推移も表示する。
- **関連ストーリー**: DB-02
- **優先度**: Must

```gherkin
Scenario: 12 か月の推移
  When スタッフがダッシュボードを開く
  Then 選んだ月を最後とする 12 か月分の MRR・新規契約数・解約数・入金額が月ごとに表示される（データのない月は 0）
```

### FR-005: 月の選択

- **概要**: 表示する月を選べる（既定は当月）。選べるのは過去 24 か月から当月まで。
- **関連ストーリー**: DB-02
- **優先度**: Should

```gherkin
Scenario: 前月を選ぶ
  When スタッフが前月を選ぶ
  Then KGI・KPI・推移が前月を基準に表示され、MRR は前月末の値になる
```

### FR-006: 要対応の件数

- **概要**: 支払い遅延の契約の数・トライアル終了間近（7 日以内）の契約の数を表示し、クリックで契約の一覧（状態で絞り込んだもの）に移れる。
- **関連ストーリー**: DB-04
- **優先度**: Must

```gherkin
Scenario: 支払い遅延の契約に移る
  Given 支払い遅延の契約が 1 件ある
  When スタッフが「支払い遅延」をクリックする
  Then 契約の一覧が「支払い遅延」で絞り込まれて表示される
```

### FR-007: ログイン後の最初の画面

- **概要**: 事業者を選んだ後の最初の画面をダッシュボードにする。サイドバーの先頭に「ダッシュボード」を置く。
- **関連ストーリー**: DB-01
- **優先度**: Must

### FR-008: スマートフォン対応

- **概要**: 幅 375px 以上で、コンソールの全画面を使えるようにする。
  - サイドバーは画面の幅が狭いときは隠し、ヘッダーのメニューボタンで開閉する。画面を移ると閉じる。
  - 一覧の表は、表の中だけを横にスクロールでき、ページ全体は横にはみ出さない。
  - ドロワー・ダイアログは画面の幅いっぱいに表示する。
  - ダッシュボードのカードは 1 列に並べ替える。
- **関連ストーリー**: DB-05
- **優先度**: Must

```gherkin
Scenario: スマートフォンでメニューを開いて画面を移る
  Given 幅 375px の画面でログインしている
  When メニューボタンを押して「商品・プラン」を選ぶ
  Then 商品の一覧が表示され、メニューは閉じ、ページは横にはみ出さない
```

### FR-009: 表示の権限と事業者の分離

- **概要**: ダッシュボードの閲覧は全ロール（`console.read`）、目標の設定はオーナー・管理者（新しい権限 `goal.write`）。他の事業者の数値は API でも返さない。
- **優先度**: Must

```gherkin
Scenario: 他の事業者の数値は見えない
  Given 事業者 A と B にそれぞれ契約がある
  When A のスタッフがダッシュボードを開く
  Then A の契約だけから計算した値が表示される
```

## 7. 非機能要件

| ID | 区分 | 要件 |
|---|---|---|
| NFR-001 | 鮮度 | 契約・請求のイベントの発生から 1 分以内（通常時）に指標へ反映する。画面には最終更新の時刻を表示する |
| NFR-002 | 性能 | ダッシュボードの API は、有効な契約が 10 万件の事業者でも 500ms 以内（p95）に応答する。集計は表示のたびに契約を数え直さず、イベントで更新した集計表から読む |
| NFR-003 | 正確さ | 同じイベントを 2 回受け取っても数値は変わらない（冪等）。イベントの順序が入れ替わっても、契約ごとの状態は新しい版で上書きし、古い版は無視する |
| NFR-004 | 分離 | 集計表は事業者ごとに RLS で分離する（他のモジュールと同じ） |
| NFR-005 | 拡張 | 指標の追加（例：LTV、コホート）は集計表への列・表の追加で行え、イベントの発行側を変えない |
| NFR-006 | 運用 | 集計の購読は専用のプロセス（worker-projection）で動かし、遅れても契約・課金の処理に影響しない。失敗したメッセージは DLQ に入り、再処理できる |
| NFR-007 | 見た目 | Stripe のダッシュボードを参考にする（事業者コンソールの設計 §5.6）。グラフは色だけに頼らず、数値はツールチップと表で確認できる |

## 8. スコープ外（やらないこと）

- 本書の機能を出す前の契約・請求の再集計（過去データの取り込み）。§9 #1
- 任意の期間の指定（月単位のみ）、日次以外の粒度（週次など）
- コホート分析、LTV、顧客単位の分析、プラン別・商品別の内訳
- CSV などへの出力、メールでの定期レポート
- 割引（クーポン）を差し引いた MRR、為替・複数通貨
- 運営者（プラットフォーム全体）向けのダッシュボード
- ネイティブのスマートフォンアプリ、オフライン対応、タブレット専用のレイアウト
