# PdM 決定ログ（TL からの確認事項への回答）

この文書は、TL から上がった確認事項に対する PdM の決定を記録する。決定は 00-poc-charter.md と同じ効力を持つ。01-contracts-baseline.md を変える決定は、ベースラインにも反映する。

| P-IDN-1 | TL-Identity Q1 | console で操作するテナントの決め方 | **A を採用する**。ヘッダー `X-Tenant-Id` で指定し、`staff_members` の制約を `UNIQUE(tenant_id, subject)` にする。設計書 §4 も直す | ベースラインを変えずに済み、将来 1 人が複数テナントに所属する形にもそのまま対応できる |
| P-IDN-2 | TL-Identity Q2 | 退会した契約者が同じログインで再登録できるか | **PoC ではできない**（403 を返す） | PoC の範囲を絞る。IdP 側で別のユーザーを作れば再登録できる |
| P-IDN-3 | TL-Identity Q3 | ベースラインへの追記（①〜⑤） | **すべて承認する**。ただし ③ の監査用イベントを記録する経路は、TL-Integration の案と合わせて決める | どれも責務と依存の向きを崩さない。④ catalog → tenant/contracts は、FR-001 を Catalog が判定するのに必要 |

| P-CAT-5 | TL-Catalog Q-05 | 割引額の計算式の置き場所 | **sharedkernel に `Discount.Apply` を置いて共用する**（TL-Platform の担当） | 申込ページのプレビューと Billing の確定額で、同じ式を使うことを保証する |
| P-BIL-1 | TL-Billing Q1 | 「決済処理中」に入るきっかけ | **A を採用する**。非同期の手段で pending を受けたときだけ processing にする。回収要求の重複は、リースと連番で防ぐ | 契約を増やさずに済む。カード決済では、processing は一瞬で終わるので見えなくても困らない |
| P-BIL-2 | TL-Billing Q2 | retryable=false の失敗 | **A を採用する**。通常の失敗と同じく段数を消費し、スケジュールを続け、支払方法の更新を促す通知を出す。支払方法が使えない（削除済みなど）場合は、Payments が決済代行を呼ばずに failed を返す（FR-021 の 3 つ目のシナリオ） | 契約者がカードを更新すれば、すぐに再決済（FR-017）で回収できる。リトライの経路を 1 つにそろえる |
