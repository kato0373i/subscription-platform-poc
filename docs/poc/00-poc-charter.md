## 1. PoC の目的

1. 設計の中核（調停役・Outbox・決済の抽象化・冪等性）が、**実際に動くコードとして成り立つ**ことを示す。
2. 申込・更新・支払い失敗・回収・解約・事業者の停止という**課金のライフサイクル全体**を、ローカル環境（MiniStack）で通して動かす。
3. 将来の拡張（決済手段の追加、従量課金、領収書）が、**既存のコードを変えずにできる構造**になっていることを、インターフェースの形で示す。

**作り込まないもの**：本番の運用品質（Multi-AZ、WAF、MFA、ダッシュボード）、UI の作り込み、性能のチューニング。

## 2. 残っていた仮定の確定（PdM 決定）

| # | 決定 | 理由 |
|---|---|---|
| D-01 | 事業者を停止したとき、トライアル中・有効な契約は**期間が終わってから**解約する。支払い遅延の契約はすぐに解約する | 返金機能がないので、契約者が払った期間は使えるようにする |
| D-02 | 支払いが遅れている間は、次の期間の請求を作らない | 未払いの債権が積み上がるのを防ぐ |
| D-03 | 支払いが遅れている契約を契約者が解約したら、すぐに解約済みにし、未払いの請求は無効にする | 支払われていない期間を使わせる理由がない |
| D-04 | ダウングレードも、次の更新日から切り替える | アップグレードと揃えて、日割りをなくす |
| D-05 | 有効な契約（トライアル中・有効・支払い遅延）が残っている契約者は、退会できない | 課金と、カードを持たない契約が食い違うのを防ぐ |
| D-06 | 本番設計では Multi-AZ を維持する。PoC はローカル（MiniStack）で検証するので対象外 | 稼働率 99.9% のためには必要 |
| D-07 | 非機能要件の目標値は、本番用として維持する。PoC では、**更新課金 1 万件をローカルで処理するスループット**だけを計測し、参考値として記録する | PoC で性能を作り込まない |
| D-08 | プランの価格は 1 円以上 1,000,000 円以下とする（税込） | 誤入力の防止 |
| D-09 | 内税の消費税額 = floor(税込額 × 税率 ÷ (1 + 税率))。税率は価格バージョンに持たせる（PoC は 10% だけ）。計算は整数と有理数で行い、浮動小数点を使わない | 領収書（NFR-012）に備えて、税額の内訳を残す |
| D-10 | 定率クーポンの割引額 = floor(税込額 × 率)。割引後の金額は 0 円未満にしない | 端数の扱いを明確にする |
| D-11 | 期間は**開始日と終了日の両方を含む**日付の範囲とする（例：10-15〜11-14）。次の更新日 = 終了日 + 1 日 | 要件定義書の受け入れ条件と揃える |
| D-12 | トライアル期間 = 申込日から trial_days 日間（申込日を 1 日目とする）。初回の課金日 = 申込日 + trial_days。それ以後は、初回の課金日を基準日（anchor）にして更新日を計算する | 計算の基準を 1 つにする |

## 3. 設計書から変えた点（PdM 決定）

| # | 変更 | 理由 |
|---|---|---|
| C-01 | **Orchestration への入力のうち、イベントで届くものは標準の SQS で受け取る**。契約ごとに処理を直列にするのは、DB の楽観ロック（`version`）と、`billing_cycle_processes` の部分ユニーク制約で行う。FIFO キューは、更新処理のジョブ投入（SDK から `MessageGroupId=subscription_id` を指定して直接送る）にだけ使う | EventBridge から FIFO キューに送るとき、MessageGroupId を契約ごとに動的に変えられないため（設計書 §6.2 の補足を置き換える） |
| C-02 | 申込のように同期で進める処理では、Orchestration が Payments の結果を受け取ったら、**`Billing.RecordPaymentOutcome` を直接呼ぶ**。あとからイベントで同じ結果が届いても、`attempt_id` で冪等に処理するので二重にならない | 申込の応答（p95 3 秒）をイベントの到着待ちにしない |
| C-03 | 料金の計算（PricingScheme）は Catalog が持つ（`QuotePrice`）。割引と税額の計算は Billing が行う（請求明細を作るため） | 責務の境界を明確にする |
| C-04 | 支払方法の削除と、契約の支払方法の変更は、**Orchestration のユースケース**にする（Payments が契約を知らなくて済むようにするため）。API のパスは設計書のとおり | Payments → Subscription の依存を作らない |
| C-05 | ~~実行基盤を Lambda 中心にする~~ → **取り消し**（P-ARC-10）。実行基盤は ECS Fargate のモジュラーモノリス（設計書 ADR-001）とする。PoC の完了条件は、ローカルで各プロセス（api・worker-billing・worker-integration）を起動して E2E が通ることとする | 依頼者（オーナー）の方針の変更（サーバーレスは好みであり標準ではない） |
| C-06 | **ローカルの DB は MiniStack の RDS で動かす**（設計書 ADR-008、P-ARC-5）。フォールバックは `DB_MODE=container` | 依頼者（オーナー）の方針。本番と同じ Terraform モジュールで DB を作る |

## 5. PoC 共通の決定

- **時刻の制御**：すべての処理は `Clock` から現在時刻を受け取る。ローカルの環境に限り、時刻を進められるようにする。
  - `POST /v1/dev/clock`：時刻を進める
  - `POST /v1/dev/jobs/{job}/run`：スケジュールで動くジョブを手動で実行する
  - 更新・リトライ・トライアル終了の予告を、テストで再現するために使う。本番のビルドには含めない（ビルドタグで除外する）。
- **ID**：内部の ID は UUIDv7 とする。外部に出す ID のうち、事業者ごとの契約者 ID は `cus_` で始まるランダムな ID、Webhook のイベント ID は `evt_` で始まる ID にする。それ以外は UUID の文字列のまま出す。
- **言語・構成**：Go の単一モジュール。構成は設計書 §1.2 に従う。
- **受け入れの単位**：ドメインごとの詳細要件に書く受け入れ条件は、Go のテストとしてそのまま書ける粒度にする。
- **PoC の完了条件**：E2E-001〜022（orchestration.md §11b）を **Playwright のテスト**として CI で通すこと。あわせて、UT（純粋なドメインロジック）と Go の結合テスト（本物の DB）も通すこと（P-TST-1〜7）。
- **テストの方針**：E2E（Playwright）を中心にし、モックは原則として使わない。DB は本物を使い、E2E から DB の値も確かめる。例外は、制御できない外部（fincode → StubAdapter、Webhook の送信先 → `webhook-sink`、認証 → 開発用 JWT、時刻 → dev clock）だけ（P-TST-2）。
